# Роли и доступ

Один механизм — realm-роли Keycloak. Группы, client-роли и атрибуты для авторизации не
используются: одна модель, один claim, одно место, где смотреть.

## Пространство имён

| Роль | Кто получает | Что даёт |
|---|---|---|
| `admin` | оператор стенда | всё: `/admin/*`, хосты с `policy: admin`, консоль Keycloak |
| `svc:<service>:admin` | владелец сервиса | полный доступ к сервису + право править роли этого сервиса у других |
| `svc:<service>:family` | семья | обычный доступ к сервису |
| `svc:<service>:blocked` | — | явный запрет на сервис при живом аккаунте |

`<service>` — ключ из `services:` в `gateway/config.yaml`: `storage`, `image`, `rag`,
`audio`. Это сервисы, у которых есть собственный уровень доступа. Хаб (`filenkov.store`),
`llm`, `observer` и `meet` живут на глобальных политиках (`public`/`admin`/`session`) и
per-service ролей не имеют — колонка без поведения в `/admin` была бы ложью.

Новый сервис с ролями = строка в `services:` + три роли в realm (см. «Реестр сервисов»).

**Отсутствие роли = `stranger`.** Явной роли `stranger` не существует: нечего забыть
выдать, нечего чистить.

## Глобальная блокировка

Делается не ролью, а `user.enabled = false`: Keycloak не выдаст токен и не пустит в
broker. Плюс `POST /admin/realms/filenkov/users/{id}/logout` — чтобы живые сессии умерли
сразу. В `gateway` для этого нет ни списка, ни кэша: пользователь без валидного токена
просто аноним.

`svc:<service>:blocked` — не то же самое: аккаунт жив, но конкретный сервис закрыт
(например, доступ к файлам отозван, а чат оставлен).

## Уровни доступа к сервису

```
                 нет роли      :family        :admin        :blocked
public host      ✓             ✓              ✓             ✓        (политика public)
session host     ✓(вход)       ✓              ✓             ✗ 403
service host     ✗ 403         ✓              ✓             ✗ 403
admin host       ✗ 403         ✗ 403          ✓(global only) ✗ 403
```

- `public` — статика витрины, `/health`, `/auth/*`. Вход не требуется.
- `session` — любой аутентифицированный с живым аккаунтом.
- `service(<svc>, family|admin)` — нужна роль `svc:<svc>:family` или `svc:<svc>:admin`.
- `admin` — только `admin`.

## Право менять роли

| Действие | Кто может |
|---|---|
| `PUT /admin/users/{id}/roles/{service}` | `admin` или `svc:{service}:admin` |
| `PATCH /admin/users/{id}` (enabled) | только `admin` |
| `PUT /admin/users/{id}/admin` (выдать/снять `admin`) | только `admin`, и не себе, если ты последний |

Проверки делает `gateway` (см. `gateway/admin.md`), а не Keycloak: Admin API у
service-аккаунта один на всех, поэтому «кто именно вызвал» решается на edge.

## Реестр сервисов

Единственный список сервисов — `gateway/config.yaml` → `services:`. Из него рендерятся:

- проверки политики (`service(storage, family)` проверяет существование ключа при старте);
- список сервисов в ответе `/auth/session` (витрина рисует по нему ссылки);
- колонки в UI `/admin`.

Добавление сервиса (4 места, все в одном коммите):

1. `gateway/config.yaml` → `services: [..., "notes"]` и блок хоста;
2. `idp/realm.json` → роли `svc:notes:admin`, `svc:notes:family`, `svc:notes:blocked`;
3. `proxy/Caddyfile` → сайт-блок с одним `reverse_proxy gateway:8080`;
4. DNS: A-запись `notes.filenkov.store` (или запись в dnsmasq для LAN-only).

## Чего в модели нет (и почему)

| Нет | Почему |
|---|---|
| Глобальная роль `family` | «семья» — свойство сервиса, а не человека; глобальный уровень давал ложные ожидания |
| Иерархии ролей | уровней три, иерархия не нужна: `admin` включает `family` правилом политики, а не графом |
| Групп | группы нужны, когда ролей сотни; здесь 8 сервисов × 3 уровня |
| Per-service администраторов через fine-grained admin permissions Keycloak | нестандартно, тяжело проверяется; проверка в gateway — 20 строк и табличный тест |
