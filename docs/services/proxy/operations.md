# proxy — эксплуатация

## Файлы

| Путь | Что |
|---|---|
| `proxy/Caddyfile` | конфиг сайтов (в git) |
| `/etc/caddy/Caddyfile` | симлинк на `proxy/Caddyfile` (единый источник) |
| `/var/lib/caddy/.local/share/caddy/` | сертификаты ACME и приватный CA (не бэкапится, восстанавливается) |
| системный + NSS store | корневой сертификат локального CA для `meet.filenkov.store` |

## Применение изменений

```bash
caddy validate --config proxy/Caddyfile        # синтаксис + проверка сайтов
systemctl reload caddy                         # без разрыва соединений
journalctl -u caddy -n 50 --no-pager           # если reload не прошёл
```

Полный рестарт (`systemctl restart caddy`) нужен только при смене `default_bind` или
глобальных опций сервера — на время рестарта TLS недоступен, то есть все продукты тоже.

## Сертификаты

| Класс | Выпуск | Продление | Проверка |
|---|---|---|---|
| ACME (публичные хосты) | автоматически при первом запросе | за 30 дней до истечения, автоматически | `curl -sI https://<host> \| head -1` |
| `tls internal` (`meet`) | локальный CA Caddy | 12 месяцев, автоматически | `openssl s_client -connect 192.168.1.102:443 -servername meet.filenkov.store` |

Диагностика ACME: `journalctl -u caddy | grep -i acme`. Типовые причины отказа —
недоступный порт 80 извне, отсутствие A-записи, `CAA` запись у регистратора.

Смена приватного CA (пересоздание томов Caddy) требует **повторной установки** корня на
клиентах: без этого браузер покажет ошибку сертификата, а не 404, и это будет выглядеть
как «упал сервис».

## Что делать, если сервис «не открывается»

Три разных симптома — три разных слоя. Проверять строго по порядку:

| Симптом | Слой | Проверка |
|---|---|---|
| `SSL alert internal error`, `curl: (35)` | `proxy` | нет сайт-блока или сертификата: `grep -c '<fqdn>' proxy/Caddyfile` |
| `404 {"error":"not_found"}` | `gateway` | `curl -H 'Host: <fqdn>' http://127.0.0.1:8080/` |
| `502` | upstream | `podman exec gateway wget -qO- http://<upstream>:<port>/` |
| `403` от Caddy на `meet` | `proxy` | запрос не из LAN/WG: `remote_ip`-правило |

## Нагрузка и ресурсы

Caddy не буферизует тела и не терминирует долгие ответы: 30-минутная загрузка и SSE-чат
проходят насквозь. Ограничения: `grace_period 10s`, лимит заголовков по умолчанию
достаточен (Keycloak отдаёт cookie до ~2 КБ).

## Бэкап

Бэкапить нечего: конфиг в git, сертификаты восстанавливаются автоматически. Единственный
артефакт, который нельзя восстановить, — корневой сертификат внутреннего CA: если клиенты
его уже импортировали, лучше не терять (`caddy pki` / том `caddy_data`).
