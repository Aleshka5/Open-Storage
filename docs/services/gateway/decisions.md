# gateway — решения

Каждое решение зафиксировано с альтернативой и ценой. Пересматривать — только с новым
аргументом, а не с новым настроением.

---

## D-1. Edge — свой Go-сервис, а не Caddy `forward_auth` + ext_authz

**Альтернативы.** (a) Caddy делает маршрутизацию, `forward_auth` спрашивает отдельный
сервис авторизации; (b) `oauth2-proxy` перед каждым приложением; (c) `caddy-security`.

**Решение.** Маршрутизация, политика и проксирование — в одном процессе.

**Почему.** (1) Политика маршрута и сам маршрут — одна строка одного файла; в варианте
(a) они разъезжаются по двум конфигам, и «маршрут есть, политики нет» становится обычным
багом. (2) `forward_auth` добавляет подзапрос на каждый запрос и второй слой, где
WebSocket-апгрейд может тихо сломаться. (3) `oauth2-proxy`/`caddy-security` инжектят свои
имена заголовков, а нам нужен ровно один контракт. (4) Табличные тесты на Go покрывают
матрицу «хост×путь×роль» за секунды — конфиг Caddy так не тестируется.

**Цена.** Мы владеем кодом прокси. Ограничение — бюджет 2000 строк и семь инвариантов
([operations.md](operations.md)).

## D-2. BFF внутри gateway, а не SPA с PKCE

**Альтернативы.** SPA получает токены от Keycloak напрямую (public client + PKCE).

**Решение.** Токены живут в httpOnly cookie, ставит их gateway.

**Почему.** Девять хостов на одном домене: `Domain=.filenkov.store` даёт один вход на
все, а SPA-вариант требует либо токен в памяти каждой вкладки (и CORS на каждом API),
либо third-party cookie к `id.filenkov.store`, которые браузеры режут. Плюс XSS: при
BFF токена в JS нет вовсе. Это же рекомендует IETF в BFF-драфте.

**Цена.** У edge появляются четыре эндпоинта и обязанность обновлять токен за
пользователя (single-flight, [bff.md](bff.md)).

## D-3. Сессия — запечатанная cookie, без Redis

**Альтернативы.** Redis с серверными сессиями; подписанная (но не шифрованная) cookie.

**Решение.** AES-256-GCM cookie с `{sub, refresh_token, sid}`.

**Почему.** Состояния нет — рестарт edge не разлогинивает, бэкапить нечего, второго
контейнера с TTL-логикой нет. Шифрование, а не только подпись: refresh-токен не должен
читаться клиентом даже теоретически.

**Цена.** Нельзя «принудительно убить одну сессию на edge». Это делает Keycloak
(`users/{id}/logout`, not-before), и он же единственный, кто знает сессии. Ротация
`GATEWAY_SESSION_KEY` = разлогин всех — приемлемый и самый быстрый способ.

## D-4. Роли в токене, а не запрос в каталог

**Альтернатива.** Отдельный сервис-каталог (как User-Service), куда edge ходит за ролью
на каждый запрос.

**Решение.** Realm-роли `svc:<service>:<level>` попадают в access-токен; edge читает их
из claim'ов.

**Почему.** Убирает второй сервис из горячего пути (было: два сетевых вызова на запрос к
`storage`, ещё один на `image`) и целую категорию отказов «каталог недоступен → 503 на
всё». Снятие роли действует в пределах TTL access (5 минут) — это честная цена, ради
которой и сделан короткий TTL.

**Цена.** Каталог = Keycloak: его Admin API становится единственным способом править
роли, а «последний админ» и «админ сервиса» приходится проверять в `gateway`
([admin.md](admin.md)).

## D-5. Пространство имён ролей вместо client-ролей и групп

**Альтернативы.** Client roles (по клиенту на сервис) + protocol mappers; группы с
иерархией; отдельные realm'ы на сервис.

**Решение.** Плоские realm-роли `svc:<service>:<level>`.

**Почему.** В токене клиента появляются только роли этого клиента, поэтому вариант с
client roles требует маппера на каждый сервис (у `User Client Role` — один клиент на
маппер) и превращается в 8 почти одинаковых конфигураций. Realm-роли приходят одним
claim'ом, читаются одной строкой, проверяются одной функцией. Отдельные realm'ы на сервис
убьют единый вход.

**Цена.** Все сервисные роли видны в одном списке (для 8×3 это плюс, а не минус).

## D-6. Глобальных уровней два, а не четыре

**Альтернатива.** Повторить `ADMIN | FAMILY | STRANGER | BLOCKED` глобально.

**Решение.** Глобально только `admin`; блокировка — `enabled: false`; всё остальное —
по сервисам.

**Почему.** Глобальный `FAMILY` создавал вопрос «что он значит на хосте, у которого своя
роль», и ответ всегда был «ничего». Отсутствие роли в модели = `stranger`, отдельного
значения не нужно. Блокировка через отключение аккаунта — единственная, которая
одновременно рвёт вход, выдачу токена и живые сессии.

**Цена.** Нельзя «глобально дать семье доступ ко всему»: новая роль = явная выдача на
каждом сервисе. Это ровно то, что делает доступ понятным.

## D-7. Один контракт, одна версия

**Альтернатива.** Флаг `legacy_headers: true` на переход, две версии в токене.

**Решение.** Только v1, только `X-Auth-*`.

**Почему.** Переходный период — это код, который потом живёт годами и требует тестов на
оба режима. Стенд один, потребителей семь, все в зоне доступа: дешевле поправить их в
одном релизе, чем годами держать два контракта.

**Цена.** Один «флаговый день»: полный простой SSO до момента, пока последнее приложение
не обновлено.

---

## D-8. Конфиг без hot-reload и с fail-fast валидацией

**Альтернатива.** Watch на файл, постепенное применение, «мягкая» валидация с warning'ами.

**Решение.** Валидация на старте, любое изменение — рестарт.

**Почему.** Прошлый опыт: удалённый маршрут молча проваливался в SPA-катчолл, и «фича
пропала» диагностировалось долго. Явный `/**`, обязательный для каждого хоста, и
недостижимые маршруты как ошибка старта убирают этот класс багов. Рестарт edge стоит
доли секунды и никого не разлогинивает.

**Цена.** Нельзя править маршруты без рестарта; приемлемо, потому что edge — не
high-availability сервис.
